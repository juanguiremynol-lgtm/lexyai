- PETICION response terms are created only by peticion_register_presentation (owner/manage-checked, versioned, one RESPUESTA_PETICION_<component> deadline per component, ADMINISTRATIVO calendar via add_business_days_sql, authority-side attribution); corrections supersede, never delete, and presentation-based anchors never configure silence effects automatically — the send date is operative, not proof of receipt.
- PETICION response terms are attributed to AUTORIDAD_ADMINISTRATIVA (never JUEZ/client; deadline_attribution returns it, so evaluate-deadline-alerts skips them); their only alert producer is sync_peticion_alerts, run inside the existing evaluate_peticion_system_events job (PETICION_DEADLINE ≤3 admin business days, PETICION_OVERDUE on the business day after expiry, fingerprints peticion_{deadline|overdue}_<deadline_id>, resolved per component by trigger) — one producer, no new cron. Live status is peticion_status (invoker, read-only); MCP creation with presentation is mcp_create_peticion (atomic, idempotent, wraps mcp_create_work_item + peticion_register_presentation).
- Filings (demanda/tutela/memorial/recurso/descargos/solicitud) are recorded only via mcp_register_filing into work_item_filings (owner-read RLS, no direct writes): one event on an existing ACTIVE owned matter or exactly one new matter in the same transaction; legal_effect is always PRESENTADO_NO_ACREDITADA_RECEPCION, and a filing never creates a term — it yields PENDING_LEGAL_TRIGGER_REVIEW plus one review task. New petitions stay on create_peticion; workflow is never inferred from the authority (CPACA judicial; administrative sanctioning = GOV_PROCEDURE + subtype; jurisdictional superintendence = judicial workflow + tribunal_type).
